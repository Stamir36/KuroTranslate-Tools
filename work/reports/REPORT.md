## 3. Технические находки (форматы)

- **FPAC**: заголовок 16 Б (`"FPAC"`, `u32 n_of_files`, `u32 first_file_address`, `u32 unk=1`); запись 32 Б
  (`u32 crc32^0xFFFFFFFF`, `u32 pad`, `u64 name_off`, `u64 size`, `u64 data_off`); имена — NUL-terminated UTF-8;
  данные подряд без выравнивания. См. `work/reports/PAC_USAGE.md`.
- **`.tbl` (`#TBL`)**: `"#TBL"`, `u32 n_headers`; header 0x50 Б (имя 64 Б, `u32 crc32(имя)`, `start`, `length`,
  `count`); далее записи и **хвостовой пул** (строки/массивы, на который ссылаются 8-байтные `toffset`-указатели).
  Хвост есть у **811/844** файлов — именно его сохранение дало основной прирост обратимости.
- **`.dat` (`#scp`)**: заголовок `#scp`, `u32 hdr_off(0x18)`, `u32 n_funcs`, `u32 vars_ptr`, `u32 vars_in`,
  `u32 vars_out`; заголовок функции 32 Б; структура 12 Б. См. `STAGE_4_REPORT.md`.
- **Кодировка**: UTF-8 (не Shift-JIS) — подтверждено на `.tbl` и `.dat`.

## 4. Отличия опкодов Kyoto от Kuro no Kiseki

- База — словарь апстрима (**1451** записей на момент merge, в форке с авторскими правками — **1533**).
- На 756 сценариях обнаружено **162 новых** `(structID, cmd)`, отсутствовавших в словаре. Итог — **1698** записей.
- Все новые поименованы `Cmd_unknown_SS_CC` (полуавтомат), сгруппированы по structID:
  `1:5, 6:1, 14:1, 18:1, 22:7, 26:103, 28:44, 30:1`.
  Полный список — `work/logs/kyoto_discovered_opcodes.txt`.
- Добавлен runtime-fallback `register_discovered_command(structID, cmd)` (OP_24) — при встрече неизвестного кода
  не падать, а логировать (env `KYOTO_OPCODE_LOG`).
- Апстрим на `00_00_00.dat` падает с `KeyError (18,22)`; наш форк проходит **все 756**.
- **Не решено:** байт-точность `.dat`. Причина локализована: 4-байтные слоты указателей на строки в секциях
  output-args/struct-params кладут эквивалентные (напр. пустые) строки в разные ячейки. Доля различий
  ≈ 2.5% (2463/97650 Б на образце). Секции кода (45116 Б) и строк (10078 Б) — байт-в-байт.

## 6. Пайплайн сборки (воспроизведение)

```bash
export PYTHONUTF8=1

# 0) распаковать оригиналы (FPACker.exe unpack-all) -> work/extract/{table,script,scene}

# 1) таблицы
cd KuroTools && python tbl2json.py ../work/extract/table/<name>.tbl     # -> work/tbl_json/<name>.json
#    ...правка строк в JSON...
python json2tbl.py ../work/tbl_json/<name>.json                        # -> <name>.tbl
python ../work/tools/batch_tbl.py ../work/extract/table                # контроль: OK=842/844

# 2) скрипты
python dat2py_batch.py -i ../work/extract/script/scena                 # -> data_to_py/*.py
#    ...правка строк / strings_map.json...
python py2dat_batch.py --only-translated true                          # -> py_to_data/*.dat

# 3) собрать .pac и проверить байт-в-байт
cd .. && python work/tools/build_pacs.py --src work/extract --out work/build/pac \
        --orig "Файлы для перевода" --verify
```

Инструменты: `work/tools/{pack_fpac,build_pacs,batch_tbl,roundtrip_dat,build_translation_map,analyze_map,scan_opcodes}.py`.

## 7. Риски и ограничения

1. **`.dat` не байт-в-байт** (~2.5% указателей). Файл того же размера и функционально корректен → обязателен
   **игровой тест** диалогов перед выпуском.
2. **`t_condition_info.tbl`, `t_costume.tbl`** — не проходят round-trip; до написания Kyoto-схем собирать
   «как есть» (hex passthrough), иначе возможны ссылки на неверные строки.
3. **Byte-exact ≠ верная семантика полей.** Совпадение размера схемы ещё не гарантирует, что поле действительно
   `toffset` (схема может быть от другой игры). Для UI-текста риск мал, но при несоответствиях нужна сверка.
4. `scene.pac` — **не диалоги** (ассеты сцен: 576 `.bin` + 572 `.json`). Трогать в последнюю очередь и только
   после явного решения пользователя.
5. **Не подтверждено**, читает ли игра loose-файлы поверх `.pac`; надёжный путь — подмена `.pac` (наш пакер
   даёт EXACT). Требуется игровая проверка.
6. `push`/`deploy` не выполнялись — только локальные commit'ы.
