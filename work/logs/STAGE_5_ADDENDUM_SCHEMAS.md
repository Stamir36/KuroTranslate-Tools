# Этап 5, дополнение — покрытие таблиц текстом (после ревью)

## 1. Что было упущено
Метрика 99.8% byte-exact достигалась частично за счёт **отката на hex**: когда схема не
подходила, `tbl2json` дампил header сырыми байтами. Так таблица проходила round-trip, но её
**текст не извлекался**. Это не «в файле нет текста», а именно пробел в схемах.

Диагностика (`work/tools/diagnose_tbl_text.py`, лог `work/logs/tbl_text_gaps_before.txt`):
- **55 таблиц** с японским текстом не извлекались вообще (~18 900 строк);
- японских строк в оригиналах 39 027, извлекалось 20 132.

Пример — `t_achievement.tbl`: 413 строк (названия/описания достижений) в хвосте, в JSON — ноль.
Причина: без `-g Kyoto` подбирался вариант схемы от **другой игры** (Sora1, те же 96 байт), разметка
полей не совпадала → битый указатель → откат на hex.

## 2. Исправления
1. **`-g Kyoto`** в `tbl2json` (и в `batch_tbl.py`): для `AchievementTableData` и др. теперь берётся
   вариант `"game":"Kyoto"` → корректные строки И byte-exact. Round-trip остался **842/844**.
2. **Авто-вывод схем** `work/tools/infer_schema.py`: неизвестные байты записи описываются типом
   `data<N>` (hex passthrough → байт-точность), а 8-байтные слоты, указывающие во всех записях на
   NUL-terminated UTF-8 строку в хвосте, помечаются `toffset` (даёт текст).
3. **`work/tools/apply_inferred_schemas.py`** — массово применяет вывод с политикой
   **«оставлять только EXACT»**: если round-trip не байт-в-байт, схемы этого файла откатываются
   (регрессии недопустимы). Бэкапы — `work/backup/schemas_pre_stage7/`.
   Результат: **27/55** файлов получили схемы, из них **7 файлов дали +238 извлечённых строк** и при
   этом остались byte-exact (напр. `t_spot_discovery` 146, `t_face_anime` 52, `t_facility` 26).
   Остальные 28 файлов откатаны (инференс не дал точного round-trip), round-trip по всем 844 — 842/844.

## 3. Оставшийся пробел и его причина
Остаются **48 таблиц** без извлекаемого текста (в `MAP_INDEX.csv` статус `raw_only`):
`t_keyword` (711), `t_npc_c*` (~2 700 суммарно), `t_realtime_tutorial` (655), `t_help` (694),
`t_monster_note` (245), `t_lookpoint` (199), `t_place` (131), `t_shop_normal` (122), `t_musubi` (116) и др.

Точная причина (разобрано на `t_keyword`): в записи есть **массив из одного 2-байтового элемента**
(`<u64 ptr><u32 count=1>`), а его данные пишутся в хвост рядом со строками. Парсер/упаковщик знают
только `u32array` (элемент 4 байта), поэтому такой массив не воспроизводится (`data<N>` сохраняет
только inline-часть ptr/count, а данные теряются) → round-trip не совпадает, и схема откатывается.

**Следующий шаг для закрытия:** добавить в `lib/parser.py`/`lib/packer.py` типы
`u16array`/`u8array` (элемент 2/1 байт, с правилами выравнивания), учесть их в `infer_schema`
(искать пары `<u64 ptr><u32 count>`, где `ptr + count*size` лежит в хвосте) и повторить
`apply_inferred_schemas` — это должно снять большинство из 48 файлов.

## 4. Карта перевода
Чтобы карта была **полной уже сейчас**, `build_translation_map.py` для таблиц без схемы добавляет
строки, просканированные прямо из `.tbl` (kind=`tbl_raw`, статус `raw_only`). Итог:
`tables.jsonl` 21 363 → **35 170** строк; всего в карте **68 998** записей.
Строки `tbl_raw` пригодны как глоссарий/QA; их правка станет возможна после появления схем
(см. §3).

# Круг 2 — полноценный вывод схем с массивами

## 6. Что добавлено
Инференс переписан на **уровень файла** (`infer_schema.infer_file`):
- хвост ОБЩИЙ для всех header'ов, поэтому раскладки выводятся совместно, с накоплением
  точной длины пула;
- распознаются не только `toffset`, но и **массивы** `u32array`/`u16array`/`u8array`
  (`<u64 ptr><u32 count>`; парсер и упаковщик уже поддерживают любой uX-array — элемент = bits/8,
  с выравниванием, как и делает `pack_data`);
- `count == 0` — законный пустой массив (указатель упаковщик всё равно перепишет, как и оригинал);
- **пустая строка** (указатель на одиночный NUL) — допустима;
- результат перебора полей проверяется **полной симуляцией сборки пула**: собранный хвост обязан
  совпасть с исходным байт-в-байт. Только тогда раскладка считается верной;
- среди подходящих раскладок выбирается с максимумом `toffset`-полей (максимум текста).

`apply_inferred_schemas.py` переведён на новый API и политику **«оставлять только EXACT»**
(иначе схемы файла откатываются).

## 7. Результат круга 2
- `t_keyword` закрыт: раскладка `data16 + u16array@0x10 + data4 + 3×toffset` → **EXACT + 264 строки**.
- На 55 «потерянных» таблицах: **17 EXACT с текстом** (было 7), +916 строк
  (`t_keyword` 264, `t_spot_discovery` 146, `t_musubi` 138, `t_chat` 109, `t_todo` 73,
  `t_face_anime` 52, `t_dungeon_quest` 46, `t_btlsys` 42, `t_facility` 26 …).
- Полный batch: **842/844 byte-exact, 0 ошибок** (без регрессий).
- Карта: `tables.jsonl` = 34 804; таблиц с извлекаемым текстом 603 (было 590).

## 8. Остаток (41 таблица) и точные причины
Не выводятся: `t_place`, `t_npc_c*` (13 файлов, ~2 700 строк), `t_help` (694),
`t_realtime_tutorial` (655), `t_monster_note` (245), `t_lookpoint` (199), `t_shop_normal` (122),
`t_monster_*`, `t_action_course`, `t_soul_ability_tree`, `t_skill`, `t_status`, `t_chr_name`, `t_dlc`,
`t_condition_info`, `t_costume` и др.

Разобрано на `t_place` (`PlaceParam`, 120 Б): в записи **≈7 указателей на строки**, а не 5;
поля 0x20/0x30/0x40 указывают на ОДНУ строку, и часть хвоста (459 Б из 22 770) не покрывается
строками вовсе. Даже с дедупликацией строк симулятор не воспроизводит хвост
(3 592 vs 22 770 байт). То есть этим таблицам нужны:
1. **дедупликация строк при сборке** (один текст — один указатель, повторно используется);
2. семантика **нулевого указателя** как «нет строки» (сейчас `readtextoffset(0)` читает заголовок файла);
3. поля, не сводимые к `toffset`/`uXarray` (например массивы строк или иные структуры),
   на которые приходится оставшаяся часть хвоста.

Такие файлы остаются в режиме **hex passthrough** (byte-exact, но без извлекаемого текста);
их строки доступны в карте как `tbl_raw`. Каждый следующий тип поля расширяет покрытие —
механика вывода уже готова, нужно добавить сами типы в `lib/parser.py`/`lib/packer.py`
и в перебор `infer_schema`.
