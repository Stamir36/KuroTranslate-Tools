## 2. Два критичных бага, найденных и исправленных (пишем байт-в-байт стал возможен)
1. **Маркеры строк (opcode 0x26, ADDLINEMARKER).** При `--markers False` дизассемблер выбрасывает их из `.py`, а ассемблер их не пишет → потеря ровно 3 байта × 1269 = **3807 байт** кода (`00_00_00.dat`). Решение: **использовать `--markers True`** (проверено: код совпал 1:1: 45116 байт). Замер — `work/tools/opcode_bytes.py`, данные `work/stage4/bytes_orig.json` / `bytes_new.json`.
2. **Дедупликация строк.** Ассемблер писал каждую строку отдельно; оригинал Falcom переиспользует часть ячеек. Правило (выведено эмпирически): `code`/`names`/`varout` — дубли сохраняются; `struct params` — дедуплицируются в общий пул. Это убрало расхождение размера (−1909 → 0). Реализовано в `KuroTools/disasm/ED9Assembler.py` (`compile`, `_emit_string(..., dedup=...)`).

## 5. BLOCKED-остаток (честно)
**Байт-в-байт round-trip не достигнут** для секций output-args/struct-params: одинаковые строки (в первую очередь пустые `""`) размещаются в разных ячейках строковой секции. Оригинал, судя по всему, дедуплицирует varout-строки в пул code-строк (`sys_event.*`), тогда как наша раскладка часть пишет как новые литералы в конец. Точный порядок вставки строк в компиляторе Falcom не восстановлен в отведённое время.
- Влияние: файл **функционально корректен** (код и строки совпадают, размер совпадает), но не идентичен побайтно.
- Для релиза: безопасно, если игра читает указатели по факту (что и происходит — значения указывают на валидные строки).
- План доработки: восстановить точный порядок эмиссии строк (см. `work/logs/agent_log.md`, Этап 4) — сравнение `work/tools/parse_scp.py` + дамп порядка пула.
